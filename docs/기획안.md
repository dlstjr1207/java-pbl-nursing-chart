## 1. 제품 정의

- **한 줄:** 가상 정신과 환자의 EMR 화면(환자 정보, 관찰 로그, 투약, 인계 리포트)을 보고, 간호사가 직접 **관찰 기록·투약 기록·SBAR 인계**를 작성하면 규칙 기반 점검과 AI 해설로 피드백하는 Java Swing 데스크톱 프로그램
- **대상:** 간호학부 3·4학년(1차), 1년차 간호사(2차)
- **핵심 가치(차별점):** ① 환자가 한 말(따옴표 인용)과 간호사가 관찰한 사실을 구분해 쓰기 ② 투약 기록의 약명·용량·시각을 정확히 쓰기 ③ 근무 교대 인계(SBAR)에서 빠뜨리지 않기
- **해결하려는 문제**
  - 실습생은 실제 EMR에 입력 권한이 없어 기록을 직접 써 볼 기회가 적다 (`TODO(팀)`: 근거 출처 찾기)
  - 교육용 EMR 연습이 자신감을 높인다는 해외·국내 연구가 있다 (E-15, E-16, E-17)
  - 정신과 병동 기록은 서술적이고 반복적이어서(E-07) 사실과 해석을 구분하는 훈련이 필요하다
  - 인계(SBAR)는 국내에서 표준 항목이 연구되어 있다 (E-18)
- **주의해서 쓸 주장**
  - 국내에는 교육용 전자간호기록 연구가 이미 있다(E-16). "국내에 없다"고 쓰지 않는다.
  - **"현업 표준 기록 형식"이라고 말하지 않는다.** 병원·병동마다 다르다. 우리는 **학부 교육용 기초 훈련**이다.
  - 임상 내용은 전문가 검수 없이 공개 자료로 작성했다. 결과물에 한계를 밝힌다.

## 3. 사용자 흐름 (요약)

상세 단계는 [시나리오.md](시나리오.md)에 있다.

1. **회원가입·로그인** — 처음 한 번 가입(이름, 아이디, 비밀번호, 소속·경력 단계), 이후 로그인
2. **개인 메인** — 실습 시작, 과거 실습 기록, 평가지표, 결과 패널
3. **실습 시작** — 환자 케이스가 **무작위**로 정해진다(테스트에서는 고정 가능)
4. **환자 정보 종합** — 환자 정보를 읽는다
5. **활력징후 & 이상행동 관찰** — 활력징후와 기존 관찰 로그를 읽고, 상황 브리핑을 보고 **관찰 기록을 작성**한다
6. **정규 루틴 투약 점검** — 처방과 복용표를 보고 **투약(PRN 포함)을 기록**한다
7. **SBAR 듀티 인계 리포트** — **S·B·A·R을 작성해 제출**한다
8. **제출 → 규칙 점검 → AI 해설** → 개인 메인에서 결과와 평가지표를 본다
9. **다시 실습하기** 또는 과거 기록 조회

### 화면별 상세

**① 로그인 / 회원가입 (F-13)**
- 로그인: 아이디, 비밀번호, [로그인], [회원가입]. 실패 시 "아이디 또는 비밀번호가 맞지 않습니다"(어느 쪽이 틀렸는지 알려 주지 않는다)
- 회원가입: 이름, 아이디, 비밀번호, 비밀번호 확인, 소속·경력 단계. 중복 아이디 거부. 안내 문구: "다른 서비스에서 쓰는 비밀번호를 사용하지 마세요"
- 화면 하단: "교육용 예시 · 임상 검수 전"

**② 개인 메인 (F-01, F-09, F-10, F-11)**
- 상단: 사용자 이름, [로그아웃]
- **[실습 시작]** 버튼(무작위 출제)
- **평가지표:** 총 실습 횟수, 최근 점수, **점검 항목별 평균**(R1 환자 발언·판단 구분, R6·R7 투약·수치 일치, R8 필수 입력, R9 SBAR 구성), 최근 5회 추이(숫자·막대)
- **과거 실습 기록 표:** 일시, 환자 케이스, 점수, [결과 보기]
- **결과 패널:** 방금 제출한 실습의 `잘 쓴 내용` / `누락한 내용` / `잘못 쓴 내용`, 지적된 문장의 하이라이트, `AI 해설`, `개선된 예시`, [다시 실습하기]

**③ 환자 정보 종합 (F-02)** — 읽기 전용. 인적사항, 진단, 입원 사유·주 증상, 약물 알레르기·부작용, 현재 처방, 위험 지표(자해 감시 Tier)

**④ 활력징후 & 이상행동 관찰 (F-03, F-04)**
- 보기: **활력징후**(값과 **추이 차트**), **관찰 로그**(시각·분류 태그·서술·처치·기록자·V/S), 안전 라운딩 체크 표시, **상황 브리핑**
- 입력: [관찰 기록 추가] → 시각, 근무, 분류 태그(여러 개 선택), 서술(환자 발언은 따옴표로 인용), 처치, (선택) V/S → [저장]
- 저장하면 로그에 **시각 순서**로 추가된다

**⑤ 정규 루틴 투약 점검 (F-05)**
- 보기: 처방 표, 시간대별 복용 상태, 용량 조절 이력, 혈중 리튬 농도, EPS 사정 항목(표시만), 구강 은닉 검사
- 입력: [투약 기록 추가] → 약(처방에서 선택), 용량, 경로, 시각, 결과(투여/거부/보류), 사유(PRN·거부·보류 시 필수), 처방 근거, 구강 은닉 검사(확인/미확인), 재평가 계획 → [저장]

**⑥ SBAR 듀티 인계 리포트 (F-06)**
- 보기: S·B·A·R 네 영역(디자인), R의 시간별 중재 체크리스트
- 입력: 각 영역 텍스트, R은 (시각 + 중재 항목) 행 추가 → [제출]. **S·B·A·R 중 하나라도 비면 제출 불가**

> 입력 영역 3개(④⑤⑥)와 ①②는 디자인이 없다. 와이어프레임 초안: [design/신규화면-설계.md](design/신규화면-설계.md)

## 5. 데이터

**환자 케이스 JSON** (`cases/PC-xx.json`) — [환자케이스.md](환자케이스.md)의 항목

| 항목 | 설명 |
|---|---|
| id, title, difficulty, objectives, reviewStatus | 메타. `reviewStatus`가 DRAFT면 화면에 "교육용 예시 · 임상 검수 전" |
| patient | 병실, 가명, 나이, 성별, 진단, 입원일, 입원 유형 |
| adr | 알레르기·약물 부작용 |
| riskTier | 자해 감시 단계 |
| orders[] | 처방: 약, 용량, 경로, 시간, PRN 여부 |
| regimenHistory[] | 최근 용량 조절 이력 |
| lithiumLevel | 혈중 리튬 농도 |
| vitals[] | 시각별 활력징후 (차트 포함) |
| observationLog[] | **기존 관찰 로그**(화면에 보이는 것) |
| safetyRounds[] | 안전 라운딩 항목 |
| **briefing** | **상황 브리핑**: 학생이 기록을 쓰기 위한 원자료 |
| **answerKey** | 필수 포함 요소(관찰 기록, 투약 기록, SBAR) |
| **modelAnswer** | 모범 기록 (제출 후에만 공개) |
| sbarReference | SBAR 참고 내용 |

**학생이 만드는 데이터** (사용자별)

```
User    { userId, 이름, 로그인아이디, passwordHash, salt, 소속·경력 단계, 가입일 }
Attempt { attemptId, userId, caseId, startedAt, submittedAt,
          observationEntries[{ time, shift, tags[], narrative, intervention, vitals? }],
          medicationRecords[{ drug, dose, route, time, status, reason, orderBasis, cheekingCheck, reassessmentPlan }],
          sbar{ S, B, A, R[{ time, action }] },
          checks{ R1, R2, R4, R5, R6, R7, R8, R9 }, score, aiFeedback }
```

- 계정은 사용자 PC의 `users.json`에 **솔트+해시**로 저장(JDK 내장 PBKDF2). 평문 비밀번호 저장 금지
- 서버·클라우드 DB는 쓰지 않는다. 계정은 PC마다 따로 존재한다
- 프로그램이 읽는 데이터 파일 전체 목록: [자료조사.md](자료조사.md) 6장

## 6. 기술 구조

- Java 17+, Swing + FlatLaf, Gson, `java.net.http.HttpClient`, Maven, JUnit 5
- 패키지: `app.ui`(화면별 클래스), `app.domain`, `app.cases`, `app.scoring`, `app.ai`, `app.storage`, `app.auth`
- **활력징후 추이 차트:** Swing 커스텀 그리기(Graphics2D) 또는 경량 차트 라이브러리 — `TODO(팀)`: 방법 결정. 값은 케이스 JSON의 `vitals[]`에서 읽는다
- 화면 기준 가로 1280px, 세로 스크롤 영역으로 구현
- 데이터·문구는 코드가 아니라 **리소스 파일**(JSON/텍스트)로 둔다
- API 키는 `config/ai.properties`(git 제외)에서만 읽는다. jar 하나로 실행한다

## 7. 규칙 기반 점검 기준

> 점수는 **참고용**이다. 화면에는 항목별 지적과 **어느 문장이 왜 지적됐는지**를 먼저 보여 준다. 가중치는 `TODO(팀)`.

| ID | 점검 | 판정 방법 | 대상 | 근거 |
|---|---|---|---|---|
| R1 | 환자 발언·판단 구분 | ① 환자 발언이 **따옴표로 인용**되었는가 ② **판단·진단 표현**("망상이 심함", "불안해 보임" 등)을 쓰지 않았는가 ③ 관찰 행동이 구체적(장소·행동·정도)인가 | 관찰 기록 | E-01, E-04 |
| R2 | 핵심 사실 포함 | 정답 키 항목(장소, 행동, 환자 발언, 간호, 투약) 포함 여부 — 동의어 인정 | 관찰 기록 | 정답 키 |
| R4 | 재평가 연결 | PRN 투약이 있으면 **약효 평가 계획·후속 기록**이 있는가 | 관찰 기록, 투약 기록 | E-02 |
| R5 | 용어·표현 | 낙인·비하·부적절 표현 | 모든 서술 | `TODO(팀)`: 근거 |
| R6 | 투약 기록 완결성 | 약명·용량·경로·시각·사유·처방 근거(거부·보류·PRN은 사유 필수) | 투약 기록 | 케이스 |
| R7 | **값 일치** | 약물명·용량·경로·시각이 처방과 같은가, 활력징후 수치가 케이스와 같은가 | 투약 기록, 관찰 기록 | 케이스, DS-20 |
| R8 | 필수 입력란 | 관찰 기록(분류, 서술), 투약 기록, SBAR S·B·A·R | 제출 시 | 화면 |
| R9 | SBAR 구성 | 각 영역에 필요한 정보가 있는가(S 상황, B 배경, A 사정, R 시간·행동이 있는 권고) | SBAR | E-18, 케이스 |

- **R3(위험사정)은 2차**로 미룬다(MSE·위험사정 입력 화면이 없음).
- **R7·R8은 정답이 분명해서 가장 정확하다.** R1의 판단 표현 목록은 근거 확보 후 확정한다(tasks D-06).
- **AI 해설은 점수에 반영하지 않는다.** 입력: 학생 작성문 + 케이스 ID + 점검 결과 요약. 출력(JSON): `{ strengths[], improvements[], example_rewrite }`. 호출이 실패하면 "AI 해설을 불러오지 못했습니다"와 규칙 점검만 보여 준다. 실제 환자 정보는 보내지 않는다(가상 케이스만).
