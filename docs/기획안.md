# 기획안

2026-11-23 기준. 결정 D10·D13~D30을 반영한 구현 기준 초안이다. 환자 데이터와 점검 세부 기준은 확정 전이다. 1차 초안 완성본은 2026-11-30, 최종 제출은 2026-12-14이며, 제출물은 프로그램·시연 영상·설명 PPT다(D19).

SBAR은 6가지 구성
1. 로그인 화면
2. 개인 메인 화면
3. 환자 정보 화면
4. 관찰 기록 화면
5. 투약 기록 화면
6. 차팅 작성 화면

## 목적

간호학부 3·4학년과 신규 간호사가 가상 정신과 환자의 정보를 읽고 관찰 기록·투약 기록·SBAR 인계를 연습한다. 환자의 발언과 관찰 사실을 구분하고, 기록의 누락과 수치 불일치를 확인하는 데 초점을 둔다.

AI는 실습 상황(가상 환자와 사건)을 만들고 해설을 보충한다. 점수는 생성된 **사실 데이터**와 학생 기록을 비교하는 규칙 점검이 만든다(D20). 임상 능력을 인증하거나 실제 진료를 지원하는 프로그램은 아니다. 교육용 EMR 연구와 기록 원칙의 출처 후보는 [근거표](근거표.md)에 있으며 원문 검증이 남아 있다.

### 문제 정의 (수업 '문제정의 방법' 형식)

> **간호학과 3·4학년 학생**은 임상실습에서 **실제 EMR에 직접 기록할 기회가 적어**, 환자의 발언과 관찰 사실을 구분하고 투약·인계 내용을 빠짐없이 기록하는 연습과 즉각적인 피드백을 받기 어렵다. 그 결과 **기록 누락·수치 불일치 같은 실수**가 신규 간호사가 된 뒤에야 드러나며, 이는 환자 안전과 업무 부담에 영향을 줄 수 있다. `[검증필요]` E-03, E-15~E-17

| 평가 항목 | 내용 |
|---|---|
| 범위 | 간호학과 3·4학년 실습생과 신규 간호사 (규모 `[확인필요]`) |
| 빈도 | 실습·근무 중 매 근무마다 기록과 인계가 반복된다 |
| 심각성 | 기록은 환자 안전·치료 연속성에 영향을 주고 법적 근거가 된다 (E-03) |
| 개선 효과 | 반복 연습 횟수, 점검 항목별 오류(누락·불일치) 감소를 평가지표로 측정할 수 있다 |
| 소프트웨어 적합성 | 반복되는 작업, **사람의 실수(누락·착각·불일치)를 줄이는 문제**, 자동 점검이 가능하다 |

## 첫 버전의 범위

| 항목 | 포함 | 후속 또는 범위 밖 |
|---|---|---|
| 환자 | PC-01(Figma 값과 허가 용법 원문 확인으로 팀이 확정한 기본 케이스, D28), **AI 생성 케이스**(정해진 사건 유형·허용 약물 안에서, D24·D29), 화면 개발용 DEMO 케이스(D25) | 사건 유형 확대 |
| 입력 | 관찰 기록, 투약 기록, SBAR | SOAPIE, 별도 MSE·위험사정 입력 |
| 화면 | 로그인, 개인 메인, 환자 정보, 관찰, 투약, SBAR의 기본 6화면과 회원가입 보조 화면 | PRN 전용 화면, MSE, 리튬 TDM, MMPI, To-Do |
| 결과 | 규칙 점검, 사용자별 기록과 평가지표 | 정밀 자유서술 평가 |
| 차트 | 활력징후 추이 | 불안 VAS 시계열 |
| 계정·저장 | 회원가입·로그인, 계정·실습 기록을 **MySQL**(각 PC에 설치)에 저장. 환자 케이스 원본은 JSON 리소스 | 공용 DB 서버, 클라우드 DB, 여러 PC 동기화 |
| 연동 | AI 케이스 생성(키가 있을 때), 선택 기능인 AI 해설 | 병원 EMR, 외부 약물 API, 실시간 채팅·긴급 호출 |

EPS·위험 지표는 케이스의 참고 정보로만 표시한다. 격리·강박 기록, 법적 절차 처리, 전자서명, 출력 기능은 현재 구현 목록에 없다. 시안에 보이는 부가 요소의 처리안은 화면명세에서 확인한다.

## 사용자 흐름

회원가입·로그인 → 개인 메인 → 실습 시작 → 환자 정보 확인 → 관찰 기록 → 투약 기록 → SBAR 제출 → 결과·과거 기록 조회.

실습 시작 시 AI 키가 있고 허용 약물 목록이 채워져 있으면 사건 유형을 골라 **AI 생성 케이스**로 실습한다. 키가 없거나 생성에 실패하면 검토된 **PC-01**로, PC-01이 아직 없으면 **DEMO** 케이스로 실습한다(D24, D25). AI 케이스 생성은 11/30 1차 초안에 함께 구현한다. 데이터 구조는 처음부터 두 케이스를 같은 형식으로 받도록 만든다. 테스트에서는 PC-01과 시각을 고정한다. 상세 흐름은 [시나리오](시나리오.md)에 있다.

## 데이터와 저장

케이스 파일은 `src/main/resources/cases/`에 둔다. `PC-01.json`은 AI가 생성한 케이스 하나를 사람이 검토한 뒤 저장한다(D24). 그 전까지 화면 개발에는 `demo.json`(DEMO 케이스, D25)을 쓴다. 허용 약물·용량 범위는 `allowed-drugs.json`(D26)에 둔다.

| 구분 | 주요 항목 |
|---|---|
| 케이스 | id, title, difficulty, objectives, reviewStatus, patient, adr, riskTier |
| 조회 자료 | orders, regimenHistory, lithiumLevel, vitals, observationLog, safetyRounds, briefing, sbarReference |
| 정답 자료 | answerKey, modelAnswer — 제출 후 공개 |
| 사용자 | userId, 이름, 로그인 아이디, passwordHash, salt, 가입일 (소속·경력 단계는 받지 않음, D23) |
| 실습 | attemptId, userId, caseId, startedAt, submittedAt, observationEntries, medicationRecords, sbar, checks, score, aiFeedback |

관찰 기록에는 시각·근무·태그·서술·처치·선택적 활력징후를 저장한다. 투약 기록에는 처방 식별자, 약명·용량·단위·경로·시각·결과·사유·처방 근거·구강 확인·재평가 계획을 저장한다. SBAR의 R은 시각과 중재를 가진 행 목록이다.

기존 기록과 학생 작성 기록은 구분한다. 같은 시각의 기존 기록을 다시 입력하도록 요구하지 않는다. 화면에서 제공하는 참고 자료와 제출 후 공개하는 정답도 구분한다.

### 저장 방식 (D21)

| 데이터 | 저장 위치 | 이유 |
|---|---|---|
| 케이스 원본(PC-01, DEMO, 허용 약물 목록) | `src/main/resources/cases/PC-01.json`, `demo.json`, `allowed-drugs.json` | 읽기 전용 교육 자료. Git으로 변경 이력을 남기고 리뷰한다 |
| 계정, 실습 기록(관찰·투약·SBAR), 점검 결과, AI 해설, AI 생성 케이스 | **MySQL 8 이상** | 사용자별 조회, 과거 기록, 평가지표 집계 |

- 접속은 JDBC(`mysql-connector-j`)를 쓴다. 접속 정보는 Git에서 제외된 `config/db.properties`에서 읽고, `config/db.properties.example`만 저장소에 올린다.
- 스키마는 `src/main/resources/db/schema.sql`로 관리한다. 설치 안내와 첫 실행에서 이 스크립트로 테이블을 만든다.
- 테이블(초안): `users`, `attempts`(케이스 ID, 고정/AI 생성 구분, 생성 케이스 원문 JSON, 시작·제출 시각, 점수, AI 해설 상태), `observation_records`, `medication_records`, `sbar_reports`, `sbar_recommendations`, `check_results`. 컬럼은 위 표의 항목을 따른다.
- 코드는 `UserRepository`, `AttemptRepository` 인터페이스 뒤에 MySQL 구현을 둔다. 단위 테스트는 메모리 구현을 쓰고, 저장 통합 테스트는 실제 MySQL(CI에서는 MySQL 컨테이너)로 확인한다.
- 비밀번호는 JDK PBKDF2와 사용자별 솔트로 해시해 저장하며 평문으로 저장하지 않는다. DB에는 앱 전용 계정을 만들어 쓰고 root 계정을 쓰지 않는다.
- 가입 정책(D23): 가입 항목은 아이디·비밀번호·이름. 아이디는 영문·숫자 4~20자이고 중복 불가. 비밀번호는 8자 이상. 로그인 실패 문구는 아이디와 비밀번호 중 어느 쪽이 틀렸는지 구분하지 않는다.
- **다른 팀이 사용할 때는 각 PC에 MySQL이 필요하다.** 설치와 스키마 생성 안내를 README에 제공하고, 다른 팀의 사용 방식(우리 PC 시연 / 각자 설치)을 교수님께 확인한다.
- API 키는 Git에서 제외된 `config/ai.properties`에서 읽는다.

## AI 케이스 생성 (D20)

AI는 **상황**을 만들고, 정답 판단은 프로그램이 **데이터**로 한다.

```
팀이 정함 (고정)                     AI가 채움 (매번 다름)
─────────────────                   ─────────────────────
사건 유형 목록                    →  환자 정보, 배경, 대화, 행동 묘사
허용 약물·용량 범위(허가사항)      →  처방 (범위 밖이면 버리고 다시 생성)
데이터 형식(PC-01과 같은 JSON)     →  사건 사실: 시각, 장소, 환자 발언,
                                       활력징후, 시행한 간호, 투약
                    ↓
     프로그램이 생성 결과를 검사 (형식, 필수 항목, 허용 약물·용량 범위)
                    ↓
  학생이 기록 → 규칙 점검은 생성된 사실 데이터와 대조 (R2, R4, R6, R7, R8, R9)
                    ↓
              AI는 해설만 추가 (점수에 반영 안 함)
```

| 구분 | 내용 |
|---|---|
| 팀이 고정하는 것 | 사건 유형 목록과 유형별 필수 사실 항목, 허용 약물·용량 범위, JSON 형식. 후보는 [환자케이스](환자케이스.md#ai-생성-케이스의-기준) |
| AI가 채우는 것 | 환자 정보·배경·대화·행동 묘사, 처방(허용 범위 안), 사건 사실, 상황 브리핑(학생 비공개), 원자료 메모·과제 안내(학생 화면) |
| 검사 | 필수 항목 누락, 형식 오류, 목록 밖 약물·용량 범위 밖, **정답 키 없음·정답 키의 약·용량이 처방과 다름**이면 사용하지 않고 다시 생성. 정해진 횟수를 넘으면 PC-01(없으면 DEMO)로 진행 |
| 채점 기준 | 생성된 **사실 데이터**(값). AI가 쓴 문장형 정답으로 채점하지 않는다. 모범 기록은 사실 데이터에서 만든 참고용이다 |
| 저장 | 생성된 케이스를 실습 기록과 함께 저장해 과거 기록에서 같은 환자로 재현한다 |
| 표시 | `AI 생성 · 임상 검수 전`. 실제 환자 정보는 AI에 보내지 않는다 |
| PC-01의 역할 | Figma 값과 허가 용법 원문 확인으로 팀이 직접 확정(D28, D24 수정). 키가 없는 PC의 기본 케이스, 테스트용 고정 케이스, AI 생성의 견본 |
| DEMO 케이스 | PC-01 검토 전 화면 개발용(D25). 값은 [환자케이스](환자케이스.md)의 Figma 예시 값에서만 고른다. 화면에 `DEMO · 실제 케이스 아님`을 표시하고, 채점 정답이나 만점 테스트에 쓰지 않는다 |
| 허용 약물 목록 | `allowed-drugs.json`(D26·D29): Aripiprazole PO 1일 10~30mg, Olanzapine PO 1일 5~20mg, 탄산리튬 PO 1일 600~1800mg 3회 분할, Lorazepam PO 1일 1~4mg(PRN 1회 0.5 또는 1mg `[검증필요]`). 비어 있으면 AI 생성만 끄고 나머지는 정상 동작 |

## 점검 기준

점수보다 항목별 피드백과 해당 입력 위치를 먼저 보여 준다. 아래는 프로그램의 교육용 점검 규칙이며 임상 표준 전체를 대체하지 않는다.

| ID | 점검 | 대상·판정 기준 | 배점(D30) |
|---|---|---|---|
| R1 | 환자 발언과 관찰 구분 | 관찰 서술에 환자 발언을 따옴표로 인용했는지. 판단 표현 목록(협조적, 비협조적, 이상한, 정상적, 잘 지냄, 문제없음, 불안해 보임)은 "관찰한 행동으로 바꿔 쓰세요"로 피드백만(E-04 등급 C, `[검증필요]` 교육용 예시) | 10 |
| R2 | 핵심 사실 | 정답 키의 요소(장소·행동·발언 인용·간호·투약·재평가)가 관찰 기록에 있는지. 요소별 동의어 목록으로 판정 | 20 |
| R4 | 재평가 연결 | 관찰 기록 또는 투약 기록에 재평가 계획이 있는지 | 10 |
| R5 | 용어·표현 | 근거가 등급 C뿐이라 이번 범위에서 제외 | — |
| R6 | 투약 기록 완결성 | 약명·용량·경로·시각·처방 근거. PRN·거부·보류는 사유 필수 | 15 |
| R7 | 값 일치 | 정답 키의 투약 값(PC-01: Lorazepam·1·mg·PO·09:30)과 학생 투약 기록 비교 | 25 |
| R8 | 필수 입력 | 관찰 분류·서술, 투약 기록, SBAR S·B·A·R | 20 |
| R9 | SBAR 구성 | 케이스별 S·B·A·R 요소와 R 행의 시각·중재. 피드백만 | — |
| R10 | 원자료 정리 | 원자료 메모가 있는 케이스에서 (1) 관찰 기록이 메모와 거의 같으면(메모와 같은 10글자 이상 구간이 기록의 60% 이상이거나, 40글자 이상 그대로 이어지면) "원자료를 그대로 옮겼습니다. 필요한 사실만 골라 정리하세요" (2) 관련 없는 메모의 낱말이 관찰·투약·SBAR 기록에 있으면 "관련 없는 정보가 들어갔습니다". 따옴표 안 환자 발언은 비교에서 뺀다. 피드백만(결과 화면 "피드백" 카드) | — |

점수 = 산출된 항목의 배점 합을 100점 비율로 환산한다. 케이스에 해당 정답 키가 없어 산출할 수 없는 항목은 배점에서 뺀다. R3 위험사정 점검은 후속 범위다. R1의 관찰 서술 규칙을 SBAR의 사정 영역에 그대로 적용하지 않는다.

PC-01의 정답 키·모범 기록은 [환자케이스](환자케이스.md)의 '정답 키'와 '모범 기록'에 있다. 모범 기록은 모든 점검을 통과해야 하며(만점), 제출 후에만 공개한다. AI 생성 케이스도 같은 형식의 정답 키를 가져야 같은 규칙으로 채점한다.

AI 해설의 입력은 가상 케이스와 학생 작성문, 점검 결과 요약이다. 반환 형식은 `strengths`, `improvements`, `example_rewrite`를 가진 JSON이다. AI 해설은 점수에 반영하지 않는다. 실패하면 규칙 점검 결과를 유지하고 해설을 불러오지 못했다는 상태를 표시한다.

## 기술 구성

Java 21, Swing·FlatLaf, Gson, JDK HttpClient, **MySQL 8 이상(JDBC)**, Maven, JUnit 5를 사용한다. 패키지는 `app.ui`, `app.domain`, `app.cases`, `app.scoring`, `app.ai`, `app.storage`, `app.auth`로 나눈다. 화면 문구와 케이스 데이터는 리소스로 관리한다.

기준 화면 너비는 1280px이며 긴 본문은 스크롤로 처리한다. 활력징후 차트 구현 방식과 최종 스타일은 미정이다. 실행용 JAR 패키징과 Maven Wrapper는 작업 목록에 포함되어 있다.
