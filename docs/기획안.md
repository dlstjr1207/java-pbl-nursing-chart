## 1. 제품 정의

- **한 줄:** 가상 정신과 환자의 정보와 면담 대화록을 보고 SOAPIE로 차팅하면, 규칙 기반 점검과 AI 해설로 피드백하는 Java Swing 프로그램
- **대상:** 간호학부 3·4학년(1차), 1년차 간호사(2차)
- **해결하려는 문제**
  - 실습생은 실제 EMR에 입력 권한이 없다 (근거: 신청서 서술, `TODO(팀)`: 근거 출처 찾기)
  - 교육용 EMR 연습이 자신감을 높인다는 해외·국내 연구가 있다 (E-15, E-16, E-17)
  - 정신과는 환자 발언(S)과 관찰(O)을 구분해 쓰는 훈련이 필요하다 (E-01, E-04)
- **주의해서 쓸 주장**
  - 국내에는 교육용 전자간호기록 연구가 이미 있다(E-16). "국내에 없다"고 쓰지 않는다.
  - 현업이 SOAPIE만 쓴다고 단정하지 않는다. 정신과 병동 기록은 서술적이라는 연구가 있다(E-07). 우리는 **"학부 교육용 기초 훈련 형식"** 으로 SOAPIE를 쓴다.

## 3. 사용 흐름

0. 회원가입·로그인 (처음 한 번 가입하고, 이후 로그인)
1. 환자 케이스 무작위
2. 환자 정보 확인: 인적사항, 진단, 알레르기, 처방, 활력징후, 이전 차팅 (JSON 파일)
4. 면담 대화록과 관찰 메모 읽기
5. 차팅 작성: S → O(+MSE) → A → P → I → E, 위험사정, 투약 기록
6. 제출 → 규칙 기반 점검 → AI 해설
7. 결과: 잘 쓴 내용, 누락한 내용, 잘못 쓴 내용, 개선 예시, 다시 해 보기
8. 이전 결과 조회

> 단계별 상세 흐름(화면·버튼·기대 결과)은 [시나리오.md](시나리오.md)에 있다.

## 4-1. 디자인(Figma) 기준 화면과 기능 연결 — 가안, 팀 확인 필요

**MVP 화면을 6개로 줄인다:** 로그인, 개인 메인, 환자 정보 종합, 정규 루틴 투약 점검, 활력징후 & 이상행동 관찰, SBAR 듀티 인계 리포트. 나머지 디자인(간호 기록·MSE·PRN·리튬 TDM·MMPI·To-Do)은 2차/제외다. 화면 내용은 [화면명세.md](화면명세.md)에 있다.

| 기능 | 연결되는 디자인 화면 | 상태 |
|---|---|---|
| F-01 환자 케이스 선택·출제 | 개인 메인 | **디자인 없음(새로 그림)** |
| F-02 환자 정보 패널 | 환자 정보 종합, 활력징후(화면 5) | 있음(읽기 전용) |
| F-03 관찰 기록 뷰어 | 활력징후 & 이상행동 관찰의 관찰 로그 | 있음 |
| F-04 SOAPIE 입력 폼 | **없음** | 결정 필요 |

| F-06 위험사정 입력 | **없음** (안전 라운딩·자해 위험 표시만) | 결정 필요 |
| F-07 투약 기록 | 정규 루틴 투약 점검 | 있음(입력 방식 `[확인필요]`) |

| F-13 로그인 | 로그인 | **디자인 없음(프레임 비어 있음)** |

### 결정이 필요한 것

**① 학생이 쓰는 것은 무엇인가?** 디자인의 4개 화면에는 **입력 화면이 없다.** 보이는 것은 이미 작성된 기록과 체크박스뿐이다.

| 안 | 내용 | 장단점 |
|---|---|---|
| A | **관찰 로그 + SBAR**를 학생이 작성. 로그 형식은 디자인을 따름(시각, 분류 태그, 서술, 처치, V/S) | 디자인과 가장 잘 맞음. 서술 속 환자 발언(따옴표 인용)과 관찰 사실을 구분하는 점검(R1)을 그대로 쓸 수 있음. SOAPIE는 쓰지 않음 |
| B | 4개 화면에 **SOAPIE 입력 폼을 새로 추가** | 기존 점검 기준 유지. 디자인을 새로 그려야 함 |
| **C (가안, 권장)** | A + 투약 점검 화면의 입력(복용·거부, 구강 은닉 검사). 흐름: 환자 정보 읽기 → 관찰 로그 작성 → 투약 점검 → SBAR 작성 → 제출 | 구조화된 입력(R7 수치·약물 일치, R8 필수 입력)과 서술 입력(R1)을 모두 점검 가능 |

참고: 정신과 병동 기록이 서술적이라는 연구(E-07)와 SBAR 표준 연구(E-18)는 A·C 쪽을 뒷받침한다. 다만 어느 쪽이든 **입력 화면은 새로 그려야 한다.**

**② 어떤 환자를 쓸 것인가?** 디자인은 이미 한 환자(502호, 'Schizoaffective' 표기, 아리피프라졸·리튬·로라제팜 PRN 등)의 상세한 데이터로 채워져 있다. 이는 환자케이스.md의 PC-01~03과 다르다.
- **가안(권장):** 디자인의 환자 **한 명을 PC-01로 삼는다.** 화면이 요구하는 데이터가 매우 많아서(화면명세 4장) 환자를 여러 명 만들 시간이 없다. PC-02(자살사고)·PC-03은 2차. 단, 디자인의 임상 값도 근거 확인 전이므로 `[검증필요]`로 둔다.

**③ MSE·위험사정:** 디자인에 입력이 없다. 가안은 **MVP에서 입력은 제외**하고 SBAR의 A 영역 요약 표시로만 둔다(F-05·F-06을 2차로 이동). 그러면 PC-02(자살사고)도 2차가 된다.

**④ 결과·평가지표를 어디에 보여주나:** 가안은 **개인 메인에 결과 패널과 평가지표**(항목별 점수 추이, 횟수)를 둔다. 별도 결과 화면은 두지 않는다.

**⑤ 점검 기준에 미치는 영향(가안 C 기준):**

| 점검 | 어떻게 바뀌나 |
|---|---|
| R1 S/O 분리 | 관찰 로그 서술에서 환자 발언(따옴표)과 관찰 사실을 구분 |
| R3 위험사정 | MVP에서 제외 또는 안전 라운딩 체크로 대체 |
| R4 A–P–I–E 연결 | SBAR의 A(사정)와 R(권고)의 연결로 대체 |
| R6·R7 투약·수치 일치 | 투약 점검 화면과 활력징후의 구조화 입력으로 정확도 높음 |
| R8 필수 입력란 | 관찰 로그·SBAR의 필수 칸 |

> 이 결정이 확정되면 1장의 SOAPIE 서술, 5장 데이터 모델, 7장 점검 기준, [시나리오.md](시나리오.md)를 다시 맞춘다. 지금 문서의 SOAPIE 중심 내용은 **디자인 확인 전의 기준**이다.

## 5. 차팅 데이터

```
Attempt { caseId, startedAt, submittedAt,
          S, O, MSE{13개 항목}, A, P, I, E,
          risk{자살사고, 타해사고, 질문한 문장, 환자 답변, 보호요인, 안전중재},
          meds[{약, 용량, 결과(투여/거부/보류), 시각, 사유}] }
```

```
User { userId, 이름, 로그인아이디, passwordHash, salt, 소속·경력 단계, 가입일 }
```

- 환자 케이스 데이터는 JSON으로 저장한다([환자케이스.md](환자케이스.md)의 항목 참고). 프로그램이 읽는 데이터 파일 전체 목록은 [자료조사.md](자료조사.md) 6장에 있다.
- 계정은 사용자 PC의 `users.json`에 저장하고, **비밀번호는 평문이 아니라 솔트 + 해시**로 저장한다(JDK 내장 PBKDF2). 사용자별 결과는 사용자 폴더의 JSON으로 저장한다.
- **서버와 클라우드 DB는 쓰지 않는다.** 따라서 계정은 PC마다 따로 존재한다(여러 PC에서 공유하지 않는다).

## 7. 규칙 기반 점검 기준

점수는 **참고용**이고, 화면에는 항목별 지적과 근거 문장을 우선 보여 준다.

| ID | 점검 | 판정 방법 | 근거 |
|---|---|---|---|
| R1 | S/O 분리 | S에 환자 발언이 있는가 / O에 환자 발언이 섞이지 않았는가 / O에 판단 표현이 있는가 | E-01, E-04 |
| R2 | 핵심 증상·사실 누락 | 환자 케이스 정답 키의 항목 포함 여부(동의어 인정) | 환자 케이스 정답 키 |
| R3 | 위험사정 | 직접 질문, 환자 답변 인용, 보호요인, 안전 중재 4요소 | E-05, E-06 |
| R4 | A–P–I–E 연결 | 사정에 대응하는 계획이 있고, 중재가 있으면 평가가 있는가 | E-02 |
| R5 | 용어·표현 | 낙인·비하 표현, 진단·판단을 사실처럼 쓴 표현 | `TODO(팀)`: 근거 |
| R6 | 투약 기록 | 약명·결과·시각·(거부·보류 시) 사유 | 환자 케이스 |
| R7 | 환자 정보 일치 | 활력징후·수치가 환자 케이스와 같은가 / 알레르기 언급 / **약물명·용량이 처방과 같은가** | 환자 케이스 |
| R8 | 필수 입력란 | 비어 있는 필수 항목(S/O/A/P/I/E, 해당 시 MSE·위험사정) | 화면 |

- R7·R8은 정답이 명확해서 **정확도가 가장 높은** 점검이다.
- 가중치와 점수 표기는 `TODO(팀)`: 확정 전까지 항목별 지적을 우선한다.
- **AI 해설은 점수에 반영하지 않는다.** 입력: 작성문 + 환자 케이스 ID + 점검 결과 요약. 출력: 좋은 점, 개선점, 개선 예시. 실패하면 규칙 점검만 보여 준다.

| 로컬 계정은 보안이 약하고 PC마다 따로임 | 결과물에 한계를 밝히고, 학생에게 **다른 서비스의 비밀번호를 쓰지 말라**고 안내 |
